# Features

One canonical inventory, organized by who it's for. [README.md](../README.md) covers the
same ground spread across "Key features," "Bonus features," and "How each requirement is
met" — this reorganizes it rather than duplicating it; exact counts live in README and
[CLAUDE.md](../CLAUDE.md), not here, so this file doesn't rot when a number changes.

## Learner-facing

- **Course catalogue** with category and tier filters, search.
- **Behavioural tracking** — search, clicks, dwell time, wishlist/cart/enroll — all
  feeding the interest profile in the background, no explicit rating/feedback required.
- **Personalised recommendations** (`/me`) — grounded in the real catalogue, generated by
  the LangGraph agent described in [low-level-design.md](low-level-design.md).
- **"Why these?" evidence panel** — the literal facts the agent was allowed to cite,
  shown alongside decaying interest-score bars. Nothing shown here is inferred silently;
  every claim traces to an actual event.
- **Manual refresh**, rate-limited, subject to the same trigger/budget gates as automatic
  refreshes — a user can't force unlimited model spend by hammering the button.
- **"Not interested"** — dismiss any recommended card; suppressed from every future
  recommendation (including the cold-start path), never scored as positive interest.
- **Accounts** — register/login/logout, session-cookie auth, CSRF-protected forms.
- **[Support / FAQ](../app/templates/support.html)** — what's tracked and why, how
  recommendations work, what "confidence" means, admin vs. learner accounts.

## Admin-facing (`/admin`, `role="admin"` only)

- **Operations dashboard** — SQL↔vector sync health, LLM call efficiency (% of
  opportunities where a model call was avoided and why), the agent graph read live from
  the compiled LangGraph object (so it can't drift from what actually runs), scheduler
  status.
- **Agent runs** — every run's node path, grade score, refine count, tokens, cost,
  latency, prompt versions used, and a LangSmith trace link when tracing is on.
- **Catalogue management** — create/edit/publish courses; publishing/unpublishing
  triggers a dual-write to the vector index via a transactional outbox, not a
  direct call from the request handler.
- **Manual digest send** — run the daily recommendation email job on demand.
- **Metrics** (`/metrics`, Prometheus format) and **readiness** (`/readyz`, reports
  which observability backends are actually live).

## Ranking & personalization (see [low-level-design.md](low-level-design.md) for detail)

- **Item-to-item collaborative filtering** — a third retrieval leg alongside vector and
  BM25, composed in via a second reciprocal-rank-fusion pass: courses that co-occur with
  a learner's own committed courses in *other* users' committed history. A learner with
  no history yet is unaffected — the leg only activates once there's something to reason
  from.
- **Deterministic heuristic ranker** — scores every candidate against the learner's
  structured profile (category/tag/brand/tier/price affinity) using only data already in
  memory, and skips the LLM grading call outright when it's clearly confident. Hand-set
  weights, not trained — there's no labelled outcome data at this scale to fit them from.
- **Exploration slot** — occasionally (`EXPLORE_EPSILON`, 15% default) swaps one
  recommendation slot for a genuinely under-shown course, so the same best-guess set
  can't compound its own popularity forever.
- **Synthetic interaction seed data** — `make seed` generates 24 clearly-namespaced
  synthetic learners with clustered, realistic enrollment patterns purely so the CF leg
  above has real cross-user signal on a fresh clone. Idempotent, never meant to be
  logged into.

## Responsible AI & quality (see [evals.md](evals.md) for detail)

- **Deterministic guardrails** — always-on regex rails blocking fabricated outcomes,
  urgency, discounts, prices not in the catalogue, and PII in generated copy.
- **Groundedness verification** — every recommendation is checked against the real
  candidate set and live SQL before it ships, with one automatic repair attempt and a
  deterministic fallback if repair doesn't converge.
- **PII scrubbing on the input side** — raw search-query text is redacted before it
  reaches a prompt, not just checked on the way out.
- **Prompt versioning** — every run records which prompt version produced it
  (`AgentRun.prompt_versions`), so a quality shift can be traced to the change that
  caused it.
- **DeepEval-based generation quality metrics** (`make eval-llm`) — faithfulness,
  answer relevancy, and a custom rubric mirroring the generation prompt's hard rules.
- **Adversarial red-teaming** (`make red-team`) — prompt-injection probes run against the
  real generate→verify path with a real model, plus hermetic (no-LLM) adversarial unit
  tests that run in every CI build.
- **Retrieval quality eval** (`make eval`) — recall@k / MRR against a fixed probe set.

## Platform / operations

- **Cost control at the source** — a per-request trigger policy that decides whether an
  LLM call is even worth making before the agent runs, a daily USD budget, a per-user
  daily call cap, and a circuit breaker — all enforced at the single Mesh gateway every
  model call goes through.
- **Offline-complete** — the whole app runs with `LLM_ENABLED=false` (deterministic
  embedder, template copy writer); this is the mode the entire test suite runs in.
- **Dual vector backends** (Chroma local, Pinecone managed) behind one interface.
- **Dual observability** (Logfire for the request/SQL/Mesh timeline, LangSmith for the
  agent graph trace) with the construction-order landmine documented and enforced in code.
- **Transactional outbox** for catalogue↔vector-index sync, with reconciliation and
  dead-lettering rather than a direct write from the request path.
